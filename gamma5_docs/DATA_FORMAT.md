# Data format of the gamma5 documentation site

The site is static: `site/index.html` loads JSON files from `site/data/` that the build code in `tools/` writes.
This file fixes the interface between the build code and the page. All paths are relative to `site/`.

## 1. Layout

```
gamma5_docs/
  DATA_FORMAT.md          this file
  README.md               what the site is, how to rebuild and serve it
  serve.py                loopback static server (gzip, no listing)
  tools/                  build code: Python package `gdocs` and the entry point `build_site.py`
    gdocs/mathview.py     notation and expression rendering (Symbolica MathML viewer)
    gdocs/graphs.py       Green's-function classes and their graphs (HepKIT / linnet rendering)
    gdocs/catalog.py      operator catalogue of the unbroken phase
    gdocs/broken.py       operator catalogue of the broken phase
    gdocs/theory/         theory cards (source text)
    build_site.py         runs every step and writes site/data
  site/
    index.html, assets/app.js, assets/app.css
    assets/viewer/        Symbolica pager module, static adapter `mathview.js`, math font
    data/                 generated JSON (sections 3 to 7)
    report/one_loop_gamma5.pdf
    resources/            light inputs and results (model files, order store, run report, final numbers)
```

Inputs of the build are the package `python/hepkit_renorm` of this repository and the files under
`site/resources/`. The build needs a licensed Symbolica (`SYMBOLICA_LICENSE` in the environment, never in a file).
The built `site/data` is committed, so the page is served without rebuilding.

## 2. Two value types used everywhere

**Math object `M`**. Every mathematical expression on the page is one of these, produced by
`gdocs.mathview.M(...)` from a Symbolica expression:

```json
{ "html": "<math ...>...</math>", "text": "plain-text form", "src": "Symbolica source or null", "view": null }
```

- `html`: static MathML produced by Symbolica's MathML printer. Always present; sufficient on its own.
- `view`: `null`, or the payload the Symbolica pager needs to mount an interactive viewer on this expression
  (opaque to the page; defined by `mathview`).
- The page never builds MathML itself. It calls `renderMath(el, M, {interactive})` from
  `assets/viewer/mathview.js` (section 8).

**Rich text `R`**. An HTML string with the tags `p em strong a ul ol li code sub sup span br` and inline `<math>`
elements only. Inline mathematics is already MathML (produced by `gdocs.mathview.prose`, which converts `[[ ... ]]`
spans holding Symbolica source). Cross references are anchors with data attributes and no `href`:
`<a data-report-page="57">section 4.2</a>`, `<a data-term="unbroken:ID">...</a>`, `<a data-class="CLASS_ID">...</a>`,
`<a data-theory="KEY">...</a>`. The page turns them into links.

A report reference is `{"label": "Section 4.2", "page": 57}` (page of `report/one_loop_gamma5.pdf`, 1-based).

## 3. `data/manifest.json`

```json
{ "title": "...", "subtitle": "...", "model": "sm_one_family", "loop_order": 1, "generated": "YYYY-MM-DD",
  "report_pdf": "report/one_loop_gamma5.pdf", "report_pages": 186,
  "phases": [ {"id": "unbroken", "title": "Unbroken phase", "file": "data/unbroken.json"},
              {"id": "broken",   "title": "Broken phase",   "file": "data/broken.json"} ],
  "classes": "data/classes.json", "theory": "data/theory.json", "resources": "data/resources.json",
  "status": R }
```

`status` states plainly what is generated by the automation and what is taken from the report.

## 4. Phase files `data/unbroken.json`, `data/broken.json`

```json
{ "phase": "unbroken", "title": "...", "intro": R,
  "overview": [ { "id": "S-ren", "title": "...", "math": M, "text": R } ],
  "fields":   [ Field ],
  "facets":   { "sector": [ {"id": "gauge", "label": "Gauge"} ], "type": [ ... ], "group": [ ... ], "kind": [ ... ] },
  "terms":    [ Term ] }
```

`overview` holds the master formulae shown above the table (the renormalised action as a whole and each of its parts).
`facets` gives, for every filter group, the allowed ids in display order with labels; `kind` is optional (broken phase).

**Field**

```json
{ "id": "G", "symbol": M, "name": "gluon",
  "kind": "gauge | fermion | sterile | scalar | ghost | antighost | auxiliary | source",
  "group": "SU(3) | SU(2) | U(1) | null", "ghost_number": 0, "statistics": "bose | fermi", "note": "" }
```

**Term**: one operator of the renormalised Lagrangian with definite field content.

```json
{ "id": "gauge-kin-G",
  "name": "Gluon kinetic term",
  "operator": M,
  "fields": ["G", "G"],
  "legs": 2, "ghost_number": 0,
  "sector": "gauge",
  "groups": ["SU(3)"],
  "evanescent": false,
  "types": ["tree", "pole", "finite"],
  "coefficients": {
    "tree":   { "math": M },
    "pole":   { "math": M, "decomposition": M, "note": R },
    "finite": { "math": M, "symbol": M, "note": R } },
  "total": M,
  "rules": [ { "title": "Vertex function", "legs": [ {"field": "G", "label": M} ],
               "parts": { "tree": M, "pole": M, "finite": M }, "note": R } ],
  "classes": { "pole": ["CLASS_ID"], "breaking": ["CLASS_ID"] },
  "theory": "gauge-kinetic",
  "remarks": R,
  "report": [ {"label": "Section 5.1", "page": 140} ],
  "kind": "interaction",
  "parents": ["TERM_ID"] }
```

- `id`: unique within the phase, stable between builds, characters `[A-Za-z0-9_-]`.
- `operator`: the operator alone, as it stands in the Lagrangian density, without its coefficient.
- `fields`: ids of `fields`, with multiplicity, in the canonical order of the class it belongs to.
- `types`: the parts of the renormalised action in which the operator occurs with a non-zero coefficient. Ids:
  `tree` (classical action `S_0`, including gauge fixing, ghosts and BRST source terms), `pole` (singular
  counterterm `δS^(1)`, four-dimensional operator), `evanescent` (singular counterterm on an evanescent operator),
  `finite` (finite symmetry-restoring counterterm `ΔS^(1)`), `breaking` (insertion `Δ_1 = s S_0`, not part of the
  action but listed for its Feynman rule). `evanescent: true` marks an operator that vanishes in four dimensions.
- `coefficients`: one entry per part that is present. `pole.math` includes the factor `1/(16π²ϵ)`; `finite.math`
  includes `1/(16π²)`. `pole.decomposition` (optional) writes the coefficient through the renormalisation constants
  `δZ`. `finite.symbol` (optional) is the name of the coefficient in the report (`r_α`).
- `total`: (sum of the coefficients) times the operator.
- `rules`: vertex functions in the report's convention (the Feynman rule is `i` times the vertex function, all
  momenta incoming unless a leg label says otherwise). One entry per independent leg assignment; `parts` has the
  same keys as `coefficients`.
- `classes.pole`: Green's functions whose one-loop graphs fix the singular coefficient. `classes.breaking`:
  ghost-number-one Green's functions with one insertion of `Δ_1` whose graphs enter the determination of the finite
  coefficient. Ids refer to `data/classes.json`. Either list may be empty or absent.
- `theory`: key of a card in `data/theory.json` (section 7); `remarks`: optional text specific to this term.
- `kind` and `parents` are used in the broken phase: `kind` is one of `facets.kind`; `parents` lists the unbroken
  terms (`id`s of `data/unbroken.json`) from which the term descends under `H -> H_v + φ`. The page shows the
  parents' graphs in the exposé of a broken-phase term.

Optional keys may be omitted or `null`. Unknown keys are ignored by the page.

Optional extensions used by the page when present: a term's `name_html` (R: the name with its symbols as inline
MathML; `name` stays plain text for titles and search); the manifest's `types` (`{type id: R}`, the definitions of the
five types) and `conventions` (R); a graph's `wick_sign` (the package's Wick sign in the leg order of its vertex
functions; `sign` is the closed-loop sign of the report's tables, −1 for a closed fermion or ghost loop); a legend
entry's `html` (R) in `data/classes.json`.

## 5. `data/classes.json`

```json
{ "groups":  [ { "key": "g0_VV", "title": "Gauge two-point functions", "ghost_number": 0,
                 "classes": ["CLASS_ID"], "report": [ {"label": "Section 4.2.1", "page": 44} ], "summary": R } ],
  "classes": [ { "id": "CLASS_ID", "group": "g0_VV", "ghost_number": 0, "fields": ["G", "G"], "label": M,
                 "insertion": null, "n_graphs": 12, "graphs": "data/graphs/FILE.json",
                 "result": { "pole": M, "breaking": M }, "summary": R } ] }
```

A class is a Green's function with definite external fields. `insertion` is `null` or `"Delta1"`. Class ids use the
characters `[A-Za-z0-9_.:,-]`. `group.key` is the key of the report's class of Green's functions.

## 6. Graph files `data/graphs/*.json`

```json
{ "class": "CLASS_ID",
  "graphs": [ { "id": "g0_G_G-003", "svg": "<svg ...>...</svg>", "loop": ["Q", "Q"],
                "topology": "bubble", "insertion": null, "symmetry_factor": "1/2", "sign": "-1",
                "caption": R, "contributes": { "pole": true, "evanescent": false, "breaking": false } } ] }
```

`svg` is the HepKIT / linnet drawing, self-contained (no external resources), sized by its `viewBox` and readable on
light and dark backgrounds. `loop` lists the fields on the internal lines. Files are loaded only when an exposé opens.

## 7. `data/theory.json` and `data/resources.json`

```json
{ "cards": { "gauge-kinetic": { "title": "...", "body": R, "report": [ {"label": "...", "page": 1} ] } } }
```

Card keys (every term refers to exactly one):

| key | scope |
|---|---|
| `gauge-kinetic` | gauge kinetic terms in d dimensions, field renormalisation, transversality |
| `gauge-self` | cubic and quartic gauge self-interactions |
| `gauge-fixing` | auxiliary field, linear gauge fixing, Feynman gauge, why it is not renormalised |
| `ghost` | ghost kinetic term and ghost-gauge vertex, ghost equation |
| `fermion-kinetic` | d-dimensional kinetic term, sterile partners, origin of the breaking |
| `fermion-gauge` | four-dimensional (barred) gauge vertex of the physical chirality |
| `yukawa` | Yukawa couplings |
| `higgs-kinetic` | scalar kinetic term and scalar-gauge vertices |
| `higgs-potential` | mass and quartic terms |
| `brst-sources` | source terms of the non-linear BRST variations, their role in the Slavnov-Taylor operator |
| `breaking` | the insertion Δ_1 = s S_0 and its Feynman rule |
| `ct-fields` | MS-bar field renormalisation constants |
| `ct-couplings` | MS-bar coupling and mass counterterms, beta functions |
| `ct-evanescent` | singular counterterms on evanescent operators |
| `st-gauge` | finite restoring counterterms with gauge fields only (two-, three-, four-point) |
| `st-fermion` | finite restoring counterterms of fermion-gauge vertices |
| `st-source` | finite counterterms of the source terms (renormalised BRST transformations) |
| `st-scalar` | finite restoring counterterms with scalars |
| `normalisation` | freedom of the finite counterterm (kernel of b) and the normalisation conditions |
| `anomaly` | the would-be anomaly and its cancellation |
| `broken-shift` | the shift H -> H_v + φ in the linear gauge, no R_ξ input |
| `broken-masses` | mass terms and mass counterterms, fermion masses with sterile partners |
| `broken-mixing` | gauge-Goldstone and neutral gauge mixing in the linear gauge |
| `broken-tadpole` | tadpole terms and the definition of the vacuum expectation value |
| `broken-st` | finite restoring counterterms after the shift (e.g. gauge two-point terms proportional to v²) |
| `broken-interactions` | interaction terms generated by the shift |

`data/resources.json` is a list `[ { "path": "resources/...", "title": "...", "description": "...", "bytes": 123 } ]`.

## 8. JavaScript interface of the viewer

`assets/viewer/mathview.js` is an ES module:

```js
export function renderMath(el, M, { interactive = false } = {})  // fill `el` with the expression
export function ready()                                          // Promise, resolved when the math font is loaded
```

With `interactive: true` and `M.view` present it mounts the Symbolica pager (zoom, sub-expression inspection,
pagination) fed from the pre-computed payload; otherwise it inserts the static MathML. It needs no network access
beyond `assets/viewer/`.

## 9. Python interface used by the data modules

```python
from gdocs import mathview
mathview.M(obj, *, interactive=False) -> dict    # obj: Symbolica Expression, source string in the site notation,
                                                 # or a hepkit_renorm object supported by the converters
mathview.prose(text) -> str                      # rich text with [[ ... ]] spans -> R
```

The notation (symbol names, function heads, how fields, indices, gamma matrices, projectors, group tensors,
derivatives and momenta are written) and the converters from `hepkit_renorm` objects are documented in the docstring
of `gdocs/mathview.py`.
